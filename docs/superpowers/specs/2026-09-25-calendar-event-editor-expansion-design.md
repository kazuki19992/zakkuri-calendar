# カレンダー表示・予定編集拡張 Design

## 1. 目的

カレンダーの視認性と操作性を改善し、予定編集を次の範囲まで拡張する。

- 2日ビューで祝日を読み取り専用の終日項目として表示する。
- 日付ヘッダーと終日欄の高さを安定させ、祝日の有無でdividerをずらさない。
- 今日への移動、表示切替、カレンダー表示設定を理解しやすくする。
- 予定色のコントラストを高め、色覚特性にかかわらず内容を読み取りやすくする。
- 予定作成・編集画面を、ざっくり予定ときっちり予定の双方へ対応させる。
- きっちり予定と終日予定を複数日にまたがって保存・表示できるようにする。
- 場所、メモ、色、複数通知、繰り返し規則を端末内へ保存する。
- 繰り返し予定をカレンダー上へ実際に展開して表示する。

通知は画面とDB保存形式までを対象とし、端末通知の権限要求、予約、解除は行わない。

## 2. 前提と対象外

### 2.1 前提

- 端末内SQLiteを正とするローカルファースト方針を維持する。
- 個人予定のタイトル、場所、メモを外部サービスへ送信しない。
- `exact`、`allDay`、`fuzzy`の既存予定を失わずにmigrationする。
- 週の開始曜日は現時点の設定を利用し、固定値を新しい画面へ重複して埋め込まない。
- 色だけで予定種別や状態を伝えない。タイトル、時間、時間帯ラベル、形状、アクセシビリティ情報を併用する。

### 2.2 今回の対象外

- 端末ローカル通知の予約・権限管理。
- 繰り返し予定の「この予定だけ」「これ以降」の編集・削除。
- 「今週中」「来週前半」など、複数日にわたる相対日付のざっくり予定。
- 書式付きメモエディタ、Markdown入力、画像・ファイル添付。
- 複数カレンダーの作成・削除・外部同期。
- 設定画面の設定項目。
- 未実装の1日、3日、週表示。

後続タスクは次のIssueで追跡する。

- #24: 利用者向けの書式付きメモエディタ。
- #25: 複数日にわたる相対日付のざっくり予定。
- #26: 繰り返し予定の個別・途中編集。

## 3. 実装とPRの分割

変更は依存順に4段階へ分割し、各段階を独立した`develop`向けPRにする。前段のマージ確認後に次段を開始する。

### 3.1 第1段階: カレンダー表示改善

- 祝日を2日ビューの終日欄へ表示する。
- 日付ヘッダーと終日欄の配置を固定する。
- 祝日を月ビューの予定点へ数えない。
- 今日への移動を`◎`から「今日」テキストボタンへ変更する。
- 予定の既定色を濃くし、ライト・ダーク双方の文字コントラストを改善する。

この段階ではDB schemaと予定編集画面を変更しない。

### 3.2 第2段階: サイドメニューと設定画面

- ハンバーガーボタンから左側サイドメニューを開く。
- 2日／月表示を切り替える。
- マイカレンダーの表示ON/OFFと色を示す。
- 「設定」とだけ表示する最小の設定画面へ遷移する。

表示状態は既存の`app_settings`へ保存する。色はこの段階では現在の既定色を表示し、第3段階でカレンダーの永続化された`colorId`へ接続する。

### 3.3 第3段階: 予定モデルとDB

- 複数日のきっちり予定と終日予定を表現する。
- 場所、プレーンテキストメモ、色、複数通知、繰り返し規則を保存する。
- マイカレンダーの既定色を保存する。
- 最後に開いた予定編集タブを保存する。
- 既存予定を非破壊でmigrationする。

この段階では利用者向け画面を変更しない。

### 3.4 第4段階: 予定編集と繰り返し表示

- 予定編集モーダルを再構成する。
- 追加項目と繰り返し設定UIを接続する。
- 繰り返し発生回を2日／月表示へ展開する。
- 編集・削除はシリーズ全体へ適用する。

## 4. カレンダー表示

### 4.1 2日ビューのヘッダーと終日欄

2日ビューは日付ヘッダー、終日項目、タイムラインの順で構成する。日付ヘッダーの高さは祝日名の有無に依存させない。祝日名はヘッダーの追加行ではなく終日項目へ移す。終日項目がない場合も、左右列のdivider開始位置を一致させるため、終日領域の最小高を共通化する。

終日項目は表示モデルで種別を明示する。

```ts
type AllDaySummaryItem = Readonly<{
  kind: 'event' | 'holiday';
  id: string;
  title: string;
  colorId: string;
  isInteractive: boolean;
  accessibilityLabel: string;
}>;
```

- `event`は予定編集へ遷移できる。
- `holiday`は読み取り専用で、祝日専用色を使う。
- 祝日と利用者の終日予定が同日にある場合は、祝日、利用者予定の順に並べる。
- 表示件数が領域を超える場合は省略表示を行い、アクセシビリティラベルに件数を含める。

### 4.2 月ビューの祝日

- 祝日は日付文字色、祝日名、アクセシビリティラベルで示す。
- 祝日だけの日には予定ありの点を表示しない。
- 利用者の予定が同日にある場合だけ予定点を表示する。
- 祝日用色は固定パレットと別のsemantic tokenとして定義する。

### 4.3 今日ボタン

`◎`は廃止し、「今日」と表示する44pt以上のボタンへ変更する。アクセシビリティ名は「今日へ移動」とする。期間移動中は視覚表示と`accessibilityState`の両方で無効を示す。

### 4.4 予定色とコントラスト

予定色は固定パレットから選ぶ。初期パレットは青、青緑、緑、黄土、橙、赤、紫、灰の8色とする。各項目は安定した`colorId`を持ち、コード上のregistryでライト／ダークの塗り色、文字色、利用者向けラベルを管理する。

文字色には各テーマの画面背景色を使う。ライトテーマでは明るい文字を読める濃い塗り、ダークテーマでは暗い文字を読める明るさの塗りを選ぶ。各塗り色は文字色とのコントラスト比4.5:1以上を満たすものだけを採用する。パレット追加ではDB migrationを不要にし、既存`colorId`は削除・転用しない。

ざっくり予定はグラデーションを維持するが、中央の塗りを現在より濃くする。タイトルと時間帯ラベルは濃い中央領域へ配置し、薄い端には文字を置かない。

## 5. サイドメニューと設定画面

### 5.1 サイドメニュー

ハンバーガーボタンで左から画面幅のおよそ80%を覆うoverlayを開く。背景のカレンダーは暗転させ、操作を受け付けない。

表示項目は2日／月の表示切替、マイカレンダーの表示ON/OFFと現在色、設定画面への導線に限定する。未実装の表示モードや複数カレンダーのplaceholderは表示しない。背景タップ、OSの戻る操作、項目選択で閉じる。Reduce Motion時は大きなスライドanimationを避ける。

マイカレンダーを非表示にした場合は利用者予定だけを隠す。祝日は独立した表示情報として残す。唯一のカレンダーが非表示でも予定データを削除しない。

### 5.2 設定画面

Expo Routerへ薄いrouteを追加し、feature screenに「設定」とだけ表示する。項目、永続化、説明文は追加しない。通常の戻る操作、左端スワイプ、アクセシビリティ見出しに対応する。

## 6. 予定編集画面

### 6.1 Presentation

予定作成・編集は上端を丸めた全画面モーダルとして表示する。ヘッダーの左右に同じ幅の操作領域を確保し、画面タイトルを中央へ固定する。

- 左: キャンセル。
- 中央: 「予定を追加」または「予定を編集」。
- 右: 保存。

保存中はキャンセル、保存、削除、入力の競合を防ぐ。保存ボタンの連打は同期的なlockで防止する。

### 6.2 ざっくり／きっちりタブ

- 初回は「ざっくり」を選択する。
- タブ変更時に最後に開いたタブを`app_settings`へ保存する。
- 次回の新規作成では保存済みタブを復元する。
- 既存予定の編集では、予定種別に対応するタブを優先する。

「ざっくり」は既存の日内時間帯定義を選ぶ。今回のざっくり予定は固定日付を1つ持ち、複数日にはしない。将来の日付入力不可な相対定義に備え、表示モデルは`isDateEditable`を持てる境界にするが、相対日付定義自体は追加しない。

「きっちり」は開始日・開始時刻・終了日・終了時刻を持つ。終日スイッチを日時行の横へ置き、有効時は時刻入力を隠して開始日・終了日だけを表示する。日付表示は`M月d日（曜日）`とし、内部値は`yyyy-MM-dd`を維持する。

### 6.3 フォーム項目

画面上の順序は、タイトル、タブ、日時または時間帯、繰り返し、カレンダー／色、場所、通知、メモ、編集時の削除操作を基本とする。

場所とメモはプレーンテキストとする。URLの自動リンク、チェックリスト、書式編集は#24へ分離する。

### 6.4 通知

通知は予定ごとに複数設定できる。既定候補と任意の事前時間を選択し、削除と並べ替えができる。画面には「通知は保存されますが、端末への通知はまだ行われません」と明示する。

## 7. Domain model

### 7.1 予定期間

- `fuzzy`: `anchorDate`と`temporalDefinitionId`を持つ。
- `allDay`: 開始日として`anchorDate`、利用者が選択した包含の終了日を持つ。
- `exact`: 開始日として`anchorDate`、`startTime`、終了日・終了時刻を編集状態で扱う。

既存の`ExactDuration`はmigration互換と時刻解決に利用する。新しい複数日入力は開始・終了のcalendar dateとwall-clock timeから固定durationへ変換し、24時間を超える固定durationを許可する。日数計算は固定ミリ秒加算ではなくcalendar date操作で行う。

既存の`instant`と`undetermined`は読み込み可能なまま維持し、時刻範囲を変更せず保存した場合は種別を保持する。利用者が終了日時を明示的に変更した場合は`fixed`へ変換する。

### 7.2 共通metadata

予定へ場所、メモ、任意の`colorId`、任意の`RecurrenceRule`を追加する。`colorId: null`はカレンダー既定色の継承を意味する。不明なIDは読み込み境界で既定色へfallbackし、保存値をログへ出さない。

## 8. 繰り返し

### 8.1 規則

初期版は、繰り返さない、毎日、毎週、平日のみ、毎月、毎年、カスタムを提供する。カスタムでは頻度、正の間隔、週次の曜日、終了条件を設定できる。終了条件は「なし」「指定日まで」「指定回数」とする。

規則は次のバージョン付きデータとして検証する。

```ts
type RecurrenceRuleV1 = Readonly<{
  version: 1;
  frequency: 'daily' | 'weekly' | 'monthly' | 'yearly';
  interval: number;
  weekdays: readonly number[];
  end:
    | Readonly<{ type: 'never' }>
    | Readonly<{ type: 'until'; date: string }>
    | Readonly<{ type: 'count'; count: number }>;
}>;
```

平日のみは月曜から金曜を指定した週次規則へ正規化する。毎月の基準日に該当日が存在しない月は、その月の発生回を作らず、月末へ自動移動しない。

### 8.2 発生回の展開

発生回をeventsテーブルへ複製しない。Repositoryから取得した元予定と要求範囲を純粋関数へ渡し、範囲内だけを展開する。無期限規則も取得範囲外へ展開しない。

発生回は元予定ID、発生日、表示用の安定したkeyを持つ。タップ時は元予定IDで編集画面を開く。初期版の保存と削除はシリーズ全体へ適用する。不正な規則は読み込み境界で「繰り返しなし」へfallbackする。#26で例外予定を追加できるよう、発生回keyを元予定IDと分離する。

## 9. SQLite

schema versionを1段進め、既存データを保持するmigrationを追加する。

### 9.1 calendars

`color_id TEXT NOT NULL`を追加し、既定パレットIDで埋める。

### 9.2 events

複数日終日の終了日、場所、プレーンテキストメモ、任意の予定色ID、バージョン付き繰り返し規則JSONを追加する。既存列は削除せず、新しいnullable列または安全な既定値付き列として追加する。row mapperで型、実在日付、JSON versionを検証する。

通常予定は従来どおりanchor範囲で取得する。繰り返し予定は開始日が要求範囲の終了日以前であるシリーズも取得し、domainの展開関数で要求範囲と終了条件へ絞る。無期限規則を含めても発生回を無制限に生成しない。取得条件を支えるindexを追加する。

### 9.3 event_reminders

予定と1対多の通知設定を保存する。一意ID、予定IDと外部キー、何分前かを表す非負整数、表示順を持つ。予定削除時は関連通知も同じtransactionで削除する。runtime値はすべてbound parameterで渡す。

### 9.4 app_settings

既存の設定Repository境界を拡張する。第2段階でマイカレンダーの表示状態を保存し、第3段階で最後に開いた予定編集タブを追加する。未設定・不正値はそれぞれ表示状態と`fuzzy`へfallbackする。

## 10. データフローと責務

- `src/domain`: 予定検証、期間計算、繰り返し規則、発生回展開。
- `src/data/sqlite`: migration、row validation、通知行、Repository実装。
- `src/features/events/hooks`: 編集状態、非同期保存、タブ設定、入力エラー。
- `src/features/events/components`: フォーム項目とモーダル表示。
- `src/features/calendar`: 祝日・終日・繰り返し発生回の表示モデルと画面操作。
- `src/app`: routeとRepositoryの組み立て。

UIはSQLite row、SQL、祝日ライブラリへ直接依存しない。予定保存と通知保存はRepositoryのtransaction境界内で一貫して行う。

## 11. Validationとエラー

- タイトルは空白だけを拒否する。
- きっちり予定の終了日時は開始日時より後とする。
- 終日予定の終了日は開始日以降とする。
- ざっくり予定は有効な日内定義を必須とする。
- 繰り返し間隔と回数は正の整数とする。
- 繰り返し終了日は予定開始日以降とする。
- 通知の事前時間は非負整数とし、同一予定内の重複を除去する。
- 場所とメモの未入力は空文字または`null`へ正規化する。
- 不明な色、設定値、規則versionは安全な既定値へfallbackする。

入力エラーは対応項目の直下へ日本語で表示する。Repository例外は予定本文を含まない固定メッセージへ変換する。保存失敗時はモーダルを閉じず、入力内容を維持する。

## 12. Accessibility

- すべての操作領域を原則44pt以上とする。
- タブ、スイッチ、チェック状態へroleとstateを付ける。
- 祝日、利用者予定、繰り返し予定を色だけで区別しない。
- サイドメニューを開いた間は背景へfocusを移動させない。
- モーダルとメニューを閉じた後は起点へfocusを戻せる構造にする。
- 予定色の文字コントラストは4.5:1以上とする。
- Reduce Motionを尊重する。
- 文字拡大時にヘッダー中央タイトルと左右ボタンを重ねない。
