# 祝日カレンダーと今週中の締切調整（Issue #9）

状態: 設計承認済み・実装済み。typecheck、lint、72 suites / 657 tests、iOS／Android export成功。独立レビューでCritical／Importantの指摘なし。実機未確認。

## 1. 目的と合意事項

祝日の表示を選べるようにし、希望する利用者には「今週中」の締切を土日祝から直前の平日へ繰り上げる。

ユーザーとの合意:

- 祝日カレンダーは最初は「日本／表示しない」。ほかの国・地域を後から追加できる境界を保つ。
- 計算への反映は「今週中の締切」のみ。来週前半、月末などの他の期間は維持する。
- 既定は従来どおり祝日を表示だけに使い、締切調整は無効。
- 調整結果が予定の基準日より前になる場合、翌週などへ移動せず「対象となる平日がありません」と表示して保存を止める。
- 保存済み予定の日付は設定変更によって再計算しない。

## 2. 対象と対象外

対象は設定画面、2日・月・ヘッダーの月picker・1日表示とiOSプレビューの祝日表示、今週中の新規解決、解決contextの保存・読込。端末内の日本祝日providerを継続利用する。

企業独自休日、国際祝日データ追加、一般の営業日加算、週末曜日の設定、月末や他のざっくり表現の調整、繰り返し予定の祝日移動、外部APIは対象外。「今週中」の金／土／日締切設定とカレンダー表示順の設定は独立して維持する。

## 3. 実装側の判断

- 「表示しない」では祝日カレンダーを利用しない。締切調整が有効な場合は土日のみを除外する。説明文でも明示する。
- 営業日候補は月〜金で、選択中の祝日カレンダーが返す祝日ではない日とする。
- 日本の祝日情報が対応範囲外なら、祝日がない日と推定しない。表示では未対応を示し、締切調整では期間の確定と保存を止める。
- 設定は1つのJSONオブジェクトとして保存し、表示用と計算用で別々の値を読み込まない。
- ネイティブ依存・外部通信は追加しない。

## 4. 設定モデルと保存

domainに `HolidayCalendarId = 'jp' | 'none'` と `HolidayPreferencesV1` を定義する。

```ts
type HolidayPreferencesV1 = Readonly<{
  version: 1;
  calendarId: HolidayCalendarId;
  adjustThisWeekDeadline: boolean;
}>;
```

既定値は `{ version: 1, calendarId: 'jp', adjustThisWeekDeadline: false }`。

`SettingsRepository.getHolidayPreferences()` と `setHolidayPreferences(value, updatedAt)` を追加する。既存 `app_settings` のキー `holiday_preferences` へJSONをUPSERTする。欠損、不正JSON、未知version、未知calendarId、不正booleanはオブジェクト全体を既定値へfallbackする。setterは不正なruntime値を拒否する。DBアクセス自体の失敗はfallbackせず読込・保存エラーにする。

既存テーブルと解決contextのJSON列を使用するため、schema version 6のまま列追加・seed変更は不要。旧データを一括書き換えない。

## 5. 設定UI

既存「カレンダー」セクションへ以下を追加する。

- 「祝日カレンダー」: 共通 `SingleSelectSheet` で「日本／表示しない」を選ぶ。
- 「今週中の締切を土日祝から繰り上げる」: Switch。既定OFF。
- 説明: 「保存済みの予定は変わりません。『今週中』を新しく指定するときに適用されます。」
- 「表示しない」選択時の補足: 「祝日を表示せず、締切調整では土日のみを除外します。」

両項目を同一hookで管理する。保存成功後だけ選択値を反映し、保存中の連続操作を同期ガードで抑止する。失敗時は以前の選択を維持し、読込失敗は再読み込みを提供する。締切曜日・週開始曜日のエラーは互いに消さない。保存中に戻っても、成功時は `CalendarRefreshContext.notifyChanged()` を呼ぶ。画面stateだけをunmount guardで制限する。

シート、Switch、再読み込みは44pt以上、選択状態は色以外とアクセシビリティ状態でも伝える。ライト／ダーク、文字拡大、Reduce Motionは既存共通部品に従う。

## 6. 祝日provider境界と表示

`JapaneseHolidayProvider` は日本祝日取得だけを担当し、設定の読込・保存・業務日判定を持たない。祝日カレンダー選択を解釈する小さなadapterを `src/data/holidays` へ追加し、`HolidayProvider` の外部契約とライブラリ非依存の `HolidayRangeResult` を維持する。

`jp` は既存の1970〜2050年対応と未対応判定を引き継ぐ。`none` は日付範囲にかかわらず利用者が無効化した既知の空集合（available、holidays=[]）を返す。無効をデータ未対応と混同しない。将来のカレンダー追加はIDのvalidationとadapterの委譲先を追加する形とし、汎用plugin機構は作らない。

`useCalendarView` は週開始曜日と同様、設定取得後に祝日coverageを作り、同一snapshotへ含める。変更通知で本体と月pickerを更新し、古い非同期処理が新しい設定を戻さない。失敗時は旧snapshotと表示を維持し再試行可能にする。

`useDayCalendar` もSettingsRepositoryを受け、1日表示とiOSプレビューに同じ設定を適用する。日本の対応範囲外では1日画面でも「祝日情報未対応」を表示する（現状のholidayName=nullだけでは欠落するため状態と表示を拡張する）。

「表示しない」でも日曜・土曜の曜日色は維持する。日本の祝日名、祝日専用終日項目、祝日由来の日付色だけを除去する。利用者予定は消さない。祝日を月表示の予定点へ加えない既存挙動も維持する。

## 7. 今週中の調整アルゴリズム

まず既存 `resolveRelativeDateRange` で調整前期間を計算する。従来どおり、基準日が金／土／日の設定締切を過ぎている場合、調整前締切は基準日当日になる。

調整が無効なら従来の結果をそのまま使う。有効ならdomainの純粋関数 `adjustThisWeekDeadline` へ調整前resolution、選択policy、providerで取得した祝日結果を渡す。feature hookがprovider取得を調整し、domainへライブラリ型・SQLiteを持ち込まない。

1. 探索範囲は基準日〜調整前締切の両端を含む。
2. 締切当日から `date-fns` の暦日演算で1日ずつ戻る。
3. 土日・祝日を除き、最初に見つかった日を締切にする。開始日は基準日のまま維持する。
4. 範囲内に対象日がなければ `noBusinessDay` を返す。
5. 祝日結果がunsupportedなら `unsupportedHolidayRange` を返す。選択範囲全体の祝日判定が可能なときだけ確定する。

例: 2026年3月16日（月）を基準、金曜締切、3月20日（金・春分の日）なら終了日は3月19日（木）。基準日が3月20日なら対象平日なしで保存できない。祝日カレンダーなしなら3月20日は対象の金曜日となる。土／日締切も同じ探索で直前の平日へ戻す。

土日祝は期間途中から穴として除外しない。帯は保存済みの開始〜調整後終了を連続表示し、途中にある祝日を飛ばす描画はしない。今週中のグラデーションは調整後の保存期間を基準に締切へ向けて濃くする。

## 8. 予定作成・編集と保存済み予定

新規フォームでは初回読込で締切曜日と祝日設定を取得する。今週中を指定したときだけ調整し、プレビューに調整後期間と「土日祝を考慮した締切」を表示する。基準日・締切設定・祝日policyの変更に対して同じ計算経路を利用する。

`noBusinessDay` は「対象となる平日がありません。基準日または締切設定を見直してください。」、unsupportedは「この期間の祝日情報に対応していないため、締切を確定できません。」と日時欄へ表示する。保存ボタンのdisabledと保存handler双方で防止し、タイトル・メモなどの入力を保持する。期間未確定のまま通常のざっくり予定として保存しない。

保存済み相対予定の編集は既存の「同じ時間表現なら保存期間を復元する」ルールを維持する。設定変更後もタイトル・色・場所・メモの編集だけで再計算しない。他の時間表現へ切り替えて新しく今週中を指定した場合にはフォーム読込時のpolicyで新規解決する。フォームを開いたまま設定が変わっても入力中のpolicyを自動更新せず、再度開いたときに最新値を取得する。

編集hookは「元の期間を維持中／利用者が時間表現を再指定済み」を操作状態として管理する。現在の定義IDと保存済みIDが一致するだけで元期間へ戻すと、別表現から今週中へ戻した再指定を識別できないため、この経路もテストする。

設定の祝日表示は保存済み予定にも反映するが、利用者予定の日付・解決contextは更新しない。設定変更は予定Repositoryのwriteを呼ばない。

## 9. 解決contextの互換性

既存 `FuzzyResolutionContextV1.parameterSnapshot` にoptionalな `deadlineAdjustment` を追加する。

```ts
deadlineAdjustment?: Readonly<{
  version: 1;
  calendarId: HolidayCalendarId;
  unadjustedDeadlineDate: string;
}>;
```

これは調整有効で新規解決した今週中だけに保存する。調整後締切は既存のevent.endDate、締切曜日は既存snapshotに保存する。調整を試みても締切が変わらなかった場合も記録する。無効時と旧データではフィールドなしを維持する。

parserは旧JSONを受け入れ、新フィールドがある場合はversion、calendarId、日付を検証して保持する。現状のparserが既知の締切曜日だけを再構築するため、新フィールドの保持とrow mappingの往復テストが必要。説明文はcontextの有無から作り、現在の設定で過去の調整理由を推測しない。

## 10. 日付・タイムゾーンとエラー

期間・祝日は `yyyy-MM-dd` の壁時計日付で扱い、UTC日時変換や24時間ミリ秒加算を使わない。端末タイムゾーンを変更しても保存済み日付を移動しない。祝日はカレンダー対象日そのものに対応する日本の祝日名として扱う。

無効化はknown empty、対応外はunsupported、Repositoryの失敗は読込エラーとして区別する。設定読込失敗時に既定値で新規予定を確定しない。対応外の表示を抑制するだけのために利用者予定を隠さない。
