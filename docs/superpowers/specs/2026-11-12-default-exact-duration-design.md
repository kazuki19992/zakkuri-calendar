# 正確な予定の初期の長さ設定 設計案

状態: **設計承認済み・実装中**。2026-11-12。基準commit: `5337af30bd1490e405b530a57d8f75a615582ba6`。

関連: [既定長設定 #57](https://github.com/kazuki19992/zakkuri-calendar/issues/57)、親MVP #1、安定化 #54。元設計は`2026-09-07-zakkuri-calendar-mvp-design.md` 5.4、後続の現在のeditor仕様は`2026-09-10-event-editor-and-add-flows-design.md`と`2026-09-30-event-editor-ui-design.md`を参照する。

## 1. 目的と合意済み事項

よく使う長さを設定しておき、正確な予定を毎回同じ長さへ直す手間を減らす。

ユーザーが承認した方針:

- 正確な予定の初期値は、現行画面と同じ**1時間**とする。
- 設定画面から初期の長さを変更できるようにする。

以下の選択肢、互換形式、editorの終了指定、エラー処理を含め、2026-11-12にユーザーが設計を承認した。

既定長は**新しく開くフォームの入力補助**であり、保存済み予定・繰り返しシリーズ・個別例外・開いたままのdraftを後から変更する規則ではない。

## 2. 対象と対象外

対象は設定の表示・保存・復元、新規exactの初期化、長さなし／未定を含む終了指定の表示・保存、旧設定の互換読込み、エラーからの再試行である。

対象外は既存予定の一括変更、端末通知の発火、時間表現や未定フェード時間の編集、任意分数を設定から新しく作るUI、課金・同期である。設定以外のカレンダー操作や画面構成を再設計しない。

## 3. 設定画面

既存の設定画面へ「きっちり予定」節を追加し、「予定の初期の長さ」と現在の値を1行で表示する。押下できる設定行から既存の`SingleSelectSheet`を開き、単一選択をチップで実装しない。

| 表示 | domainの値 | 意味 |
| --- | --- | --- |
| 長さなし | `{ type: 'instant' }` | 開始時刻だけが決まり、長さを持たない |
| 10分 | `{ type: 'fixed', minutes: 10 }` | 指定した長さから初期終了日時を計算 |
| 15分 | `{ type: 'fixed', minutes: 15 }` | 同上 |
| 30分 | `{ type: 'fixed', minutes: 30 }` | 同上 |
| 1時間 | `{ type: 'fixed', minutes: 60 }` | 未設定時の初期値 |
| 未定 | `{ type: 'undetermined' }` | 開始時刻は決まり、終了はまだ決まっていない |

「長さなし」は元MVPの「瞬間」と同じdomain値で、技術用語を避けるための表示名変更である。「未定」は既存の開始から薄くなる表示を使い、フェード長は既存の120分設定境界に従う。

行の補足は「新しく作る予定に使います。保存済みの予定は変わりません。」とする。選択はラベルとチェック印で識別し、色だけへ依存しない。44pt、文字拡大、読み上げ、明暗テーマ、Reduce Motionは既存共通UIの条件を引き継ぐ。

有効な旧設定に45分など候補外の固定長がある場合、丸めず「45分（現在の設定）」として一時的に現在値を表示する。新たな任意分数入力は追加しない。別候補を保存した後は通常の6候補へ戻す。

読込み中と保存中はこの設定の操作だけを無効にする。保存成功後に選択表示を確定し、失敗時は前の値を保持して再選択できるようにする。読込みに失敗した場合は再読み込みを出し、設定節だけがエラーになって他の設定を使える。

## 4. 新規フォームへの適用

### 4.1 優先順位と適用時点

1. 既存予定・繰り返し発生回・置換予定の編集は保存内容を優先し、この設定を読み込んで上書きしない。
2. 新規作成でもrouteが**終了を明示している**場合は、その開始・終了範囲を優先しfixedとして扱う。routeが自分で補った1時間は「明示」に含めない。不正な明示範囲は入力エラーとし、設定で無言に補正しない。
3. それ以外の新規フォームでは設定を一度読み、exact draftを初期化する。開始だけを指定するタイムラインのダブルタップにも適用する。

routeの開始／終了指定の有無をhookへ渡せるようにし、`src/app/events/new.tsx`にある固定の`+60`分を初期化の正本にしない。設定とrouteを解決する純粋関数をfeatureへ置き、routeは入力と依存の組立てにとどめる。

フォームが「ざっくり」で開いた場合も、背後のexact draftの初期値として一度だけ確保する。後から「きっちり」へ移っても設定を読み直さない。設定値の変化で編集中の入力を追従させない。終日を含め、タブの往復だけを理由に既定長を再適用しない。

既存fuzzy／終日を編集中にexactへ変更する場合も、既定長の変更を既存予定へ遡及させない。現行の編集用初期化を維持し、今回の設定の対象に広げない。non-fixed既存exactの種別は保存値から復元する。

### 4.2 終了の指定

きっちり・終日OFFのとき、「終了」行の単一選択を追加する。

| 終了の指定 | 表示する日時入力 | 保存 |
| --- | --- | --- |
| 時刻を指定 | 開始日時と終了日時 | 両日時からfixed分数を計算 |
| 長さなし | 開始日時だけ | instant。隠れた終了値は保存に使わない |
| 未定 | 開始日時だけ | undetermined。隠れた終了値は保存に使わない |

既定長がfixedなら「時刻を指定」、instantなら「長さなし」、undeterminedなら「未定」で開く。終了種別は`ExactDuration['type']`と対応させ、既存予定のdurationを消さずに編集・保存する。

終日ONでは終了種別を隠し、従来どおり開始日・終了日を表示する。ざっくりタブでも終了種別を隠す。隠しただけでexact draftの種別を消さない。保存時は現在のタブと終日状態を優先する。

fixedでの開始・終了日時の個別編集は現行の操作を維持し、初期設定の長さを強制し続けない。「長さなし／未定」から「時刻を指定」へ変更するときは、直近の有効なfixed分数（なければ60分）を現在の開始日時へ足して終了を作る。逆方向へ変えるときは、直近の有効なfixed分数をdraft内に保持する。無効なfixed入力から切り替えた場合、保存対象ではなくなった終了エラーを引き継がない。

日付跨ぎはカレンダー日付の加算と壁時計の分数で解決し、固定ミリ秒加算をしない。23:30＋60分なら翌日00:30とする。fixedのゼロ・負数は従来どおり拒否する。同時刻だからといってinstantへ自動変換しない。

### 4.3 設定読込み失敗

設定読込みの失敗を、初期値1時間として成功扱いにしない。新規・終了未指定のexact draftは初期化待ち／エラー状態とし、きっちり・終日OFFの日時操作と保存を止めて再読込みを表示する。

タイトル・場所・メモなどの入力を保持する。ざっくり予定や終日予定の保存は、無関係な既定長読込み失敗で妨げない。既存予定の編集・明示終了routeもこの設定の読込みを必要としない。

再試行や遅延応答はgeneration/refで扱い、unmount後や古いリクエストの完了で現在の入力を上書きしない。exact初期化が終わるまでexact日時の編集を許可しないことで、遅い初期値が利用者の日時入力を潰す競合を防ぐ。

## 5. 永続化と旧seedの扱い

既存の`app_settings`とキー`default_exact_duration`、Repositoryの`getDefaultExactDuration`／`setDefaultExactDuration`を再利用する。新しいテーブルや別の保存基盤は追加しない。domainの`ExactDuration`も変更しない。

新しい保存形式は、同じキーのJSONを次のenvelopeで保存する案とする。

```json
{ "version": 1, "duration": { "type": "fixed", "minutes": 60 } }
```

| 保持されている値 | 読込み結果 |
| --- | --- |
| キーなし、不正JSON、不正duration、未知version | 1時間 |
| 新形式version 1＋有効duration | その値をそのまま使う（明示選択したinstantも含む） |
| 旧形式`{ type: 'instant' }` | 設定UIが未提供だった時点のseedとして1時間に解釈 |
| 旧形式の有効fixed／undetermined | 既存値を維持。任意の正のfixed分数も丸めない |

旧instantが初期seedか手動書込みかは、現データだけでは完全に識別できない。今回まで通常のUIから設定値を選ぶ導線はなく、現行の新規フォームは設定によらず1時間なので、**旧instantだけは未選択seedとして扱う**判断を提案する。これは保存済み予定のinstantを変える処理ではない。手動で旧設定へinstantを書いた利用者も、新UIで「長さなし」を選べば新形式として保持できる。

過去migrationのDDL・既存行を一括変更しない。schema versionは6のままとし、旧seedはreaderの互換解釈で扱う。新形式への書込みは利用者が設定を保存した時だけ、1行のparameter付きUPSERTで行う。読込みのfallbackではDBを書き換えない。新しいDBも旧seedから論理初期値1時間として使えるため、再実行により明示選択が消えることはない。

envelopeの読込み・validation・互換解釈はSQLite Repository境界内に閉じる。未設定時の1時間というdomain既定値・表示用候補と、永続化の互換形式は責務を分ける。

元MVP設計5.4の初期値・設定名とデータ保存節は、実装PRで本設計に合わせて更新する。後続editor設計の1時間は、固定値ではなく「設定が未選択の場合の値」として位置付け直す。

## 6. 責務と変更範囲

| 層 | 変更内容 |
| --- | --- |
| domain/calendar | 既定長60分、固定候補などの正本。予定durationとRepository契約を再利用 |
| data/sqlite/settings-repository | envelopeと旧形式のparse、validation、UPSERT |
| features/settings | `useDefaultExactDurationSettings`、設定節。既存の状態管理パターンを利用 |
| features/events | 初期duration解決・終了種別・snapshot・エラー状態をhookと純粋関数へ分離 |
| shared/components | 既存の単一選択UIを利用。画面固有のduration処理は置かない |
| app | 設定hookとeditor入力の配線だけ |
| docs | 元MVP・editor・README・#54の検証記録の整合を更新 |

新しい依存パッケージ・画面route・native APIは追加しない。関数名と小さなファイル分割は実装計画で決める。大きいeditor hookの全面書換えは対象にしない。

## 7. 検証と完了条件

実装ではテストを先に書き、期待する理由で失敗したことを確認してから最小実装する。

- Repository: 欠損／旧instant／旧fixed／旧undetermined／新形式の全種別／不正値・未知version、parameter付き保存、保存失敗時の旧値保持。
- 実SQLite: 旧version 1〜5と現行DBの再起動・migration再実行後も新形式の明示選択と既存予定・通知・メモを保持する。設定変更だけでeventsを更新しない。
- 設定hook・UI: 6候補、候補外固定長の保全、ローディング、保存中連打、成功後確定、失敗保持と再試行、古い応答とunmount、読み上げ状態。
- editor: 開始のみのroute、開始終了明示、深夜・月末・年末、タブ／終日往復、既存exactの全種別、fuzzy／終日の編集、duration読込み失敗時の範囲限定、draft保存前にDBを更新しない。
- fixed／instant／undetermined間の切替と再編集、fixedゼロの拒否、無関係な設定変更が現在のdraftへ反映されないこと。
- typecheck、lint、全Jest、diff-check、iOS／Android export。native buildの必要性は使用APIと既存ビルドの互換性に応じて判断する。
- 実機では既定長設定→新規作成、日跨ぎ、終了種別、メモとの同居、再起動、明暗テーマ、文字拡大、VoiceOver／TalkBackを確認する。自動テスト・exportを実機操作の証拠に含めない。

既定長設定を実装しても#54の未確認項目は自動で完了にしない。#1の設定に関する仕様差は実装・検証後に解消済みへ更新する。

## 8. 実装者による提案の要点

1. 「瞬間」の表示名を「長さなし」とし、元MVPの6候補を引き継ぐ。
2. exactに終了種別の選択を加え、長さなし／未定を設定・編集・再保存できるようにする。
3. 同じ設定キーへversion付きenvelopeを保存し、旧seedのinstantと今後の明示選択を区別する。
4. 固定長設定を毎編集時に強制せず、新規フォーム初期化時のsnapshotとする。
