# 時間表現の範囲・フェード・未定時間の設定

## 状態と関連

- 対象: Issue #60。設計レビュー用。機能は未実装。
- ユーザー確認済み: 変更は保存済み予定にも反映する。時刻だけでなく週・月の範囲も今回の対象にする。画面モックアップは作らず設計書で確認する。
- 以下の具体的なUI、入力刻み、保存手順は実装担当の提案であり、この設計書全体の承認をもって確定する。
- 基準: MVP設計、時間軸グラデーション設計、相対日付設計4.4、繰り返し個別変更設計、端末通知設計。
- #57の「正確な予定の初期長」、#61の「相対日付の意味を保つ繰り返し」とは別機能。

## 1. 目的と適用範囲

利用者ごとの「朝」「今週前半」「月初」などの感覚を、時間表現の定義として調整できるようにする。設定後は、新規予定と同じ定義を使う保存済み予定が同じ範囲・グラデーションで表示される。

設定は現在の既定カレンダーの時間表現に適用する。終了が「未定」の表示時間は既存のアプリ共通設定を利用する。将来の複数カレンダー選択UIは追加しない。

保存済み予定には過去の予定も含む。日単位の繰り返し予定・その個別変更にも、実際に参照している定義を適用する。週・月の相対予定は現状どおり繰り返し不可とし、#61を先行実装しない。

## 2. 対象・対象外

### 対象

- 既存の標準時間表現23種類の範囲・フェード設定。
- 終了が「未定」の正確な予定を、開始から何分先まで描くかの設定。
- 保存済み予定への反映、表示の再読み込み、今後の端末通知の再予約。
- 読み込み・入力検証・保存失敗・競合・再試行・キャンセル。
- 時間表現ごとの初期値復元。

### 対象外

- 時間表現の追加、名前変更、削除、並べ替え、有効・無効の切り替え。
- 「来週」を「再来週」へ変えるような選択時の週・月オフセットの編集。
- 時間表現間の自動連動や重複解消。朝と午前が重なっていても有効。
- 確定した正確な予定・終日予定の日時変更、通知条件そのものの変更。
- 課金、テーマ、外部同期、相対日付の繰り返し、メモエディタの埋め込み。

## 3. 画面と操作

設定に「時間表現」を追加し、専用の一覧へ遷移する。既存の設定画面と同じ戻るナビゲーションを使う。一覧は「この日」「週」「月」で分類し、名前と現在の範囲を表示する。例は「朝　6:00〜10:00」「今週前半　月曜日〜水曜日」「月初　1日〜5日」。

行をタップするとその時間表現の編集画面を開く。編集画面には範囲、開始側・終了側のぼかし、プレビュー、初期値復元、保存を置く。見出し・ラベル・操作部の左端を揃え、既存のsemantic color tokenと共有選択シートを使う。キャンセル可能な選択シートの選択はローカルdraftだけへ反映する。

- 編集は保存までインメモリ。初期値復元もdraftへ反映し、即時保存しない。
- 変更なしでは保存を無効にする。変更を破棄して戻る場合は破棄確認を出す。
- 保存前に「この時間表現を使う保存済みの予定にも反映されます。今後の通知時刻が変わる場合があります」と明示する。
- 保存時に最終差分と影響件数を確認する。件数は定義を直接参照する保存済みレコード数とし、繰り返しシリーズは1件と数える。開催数と誤認させない説明を添え、削除済み開催は数えない。予定本文・タイトルを表示せず、件数と変更した設定だけを表示する。確認後に競合した場合は自動的に上書きしない。
- 成功時に一覧へ戻る。失敗時は編集内容を残してエラー・再試行を表示し、DBとカレンダー表示は保存前の状態を維持する。
- 一括保存・全項目一括リセットは設けない。1つの時間表現を1回の操作単位にする。

「未定の表示時間」は一覧の別セクションに置く。例「2時間」。既存の時間・分のドラムロールを再利用し、選択後の保存で変更する。「終了時刻や通知の基準には使われません」と表示する。保存前に変更前後の時間と、保存済み予定の表示にも反映する旨を確認する。こちらは予定を書き換えず、件数の集計は不要とする。

## 4. 範囲の編集規則

| 定義の種類 | 編集項目 | 制約 |
| --- | --- | --- |
| この日の9種類 | 開始時刻・終了時刻・終了が当日か翌日か | 1分刻み、開始0:00〜23:59、終了は開始より後、全体24時間以内 |
| 週の範囲7種類 | 開始曜日・終了曜日 | 月曜〜日曜の中で開始≦終了。同じ曜日も可 |
| 今週中 | 範囲は読み取り専用、フェードのみ編集 | 締切曜日は既存設定から変更。新規予定だけに適用する従来の規則を維持 |
| 月初・上旬・中旬・下旬・来月 | 開始日・終了日 | 開始1〜31日、終了1〜31日または月末、開始≦終了 |
| 月末 | 月末を含む日数 | 1〜31日 |

「週の範囲7種類」は今週前半・今週後半・今週末・来週・来週前半・来週後半・再来週。名前・対象週オフセットは変えない。同じ「前半」でも今週と来週の設定は独立し、片方の保存で他方は変わらない。初期値の異なる今週後半と来週後半も現状のまま保持する。

日跨ぎは「深夜　22:00〜翌日2:00」のように翌日を明記する。終了の当日・翌日を明示的に選び、開始より早い終了時刻から勝手に翌日と推測しない。既存domainの0〜1439の開始、開始より後かつ2879以下の終了、差1440以下という制約を維持する。

月の指定日は既存ルールどおり、その月の最終日へ丸める。例は「29日〜月末」が2月に28日〜28日となるケース。「来月」の翌月オフセットも維持する。週を跨ぐ曜日指定や、別月へはみ出す範囲は扱わない。

既存の初期値はすべて維持する。設定導入時にseedの値で利用者の保存値を上書きしない。

## 5. フェードとプレビュー

画面の名称は「開始側をぼかす」「終了側をぼかす」とし、範囲全体に対する長さを%で示す。通常操作は5ポイントずつ増減できる44pt以上のボタンにする。0%は「ぼかさない」。各値0〜100%、合計100%以下。合計を超える変更は他方を勝手に変更せず、操作を無効にして理由を読み上げられるようにする。

保存データは既存の0〜1の比率を使う。過去に保存された5%刻みでない有効値も、読み込みや他項目の編集で丸めない。増減は現在値から5ポイントとし、端では0%・100%および残りの上限へ制限する。表示上の丸めと保存値を混同しない。

プレビューは実際の予定ブロックと同じstop計算を使い、範囲・ぼかしをdraftから即時更新する。予定の色だけでなく名前・範囲・「開始25%、終了25%」も文字で示す。日単位は時間軸、週・月は横方向で表現する。固定の例示期間であることを示し、実際の予定日時と誤認させない。

「今週中」の既定は開始100%・終了0%。従来どおり開始から締切へ向かって濃くなる。利用者が編集した場合はその値を優先し、描画側で再度固定値を上書きしない。

終了「未定」の表示時間は1〜1440分の整数、既定120分とする。保存は既存の`undetermined_fade_minutes`の数値JSONを使う。欠落・破損・非整数・範囲外では120分にfallbackし、読んだだけでDBを書き換えない。既存seedの120分はそのまま使う。

未定は開始から設定時間をかけて薄くなる現在の描画を維持する。実際の終了日時は作らず、保存済み予定のdurationも書き換えない。瞬間予定・長さ確定予定には適用しない。

## 6. 保存済み予定への反映

### 日単位

保存済み予定は定義IDを参照し、描画と通知で最新の時刻範囲を利用する。予定のanchorDateやendDate、繰り返し規則・開催日を変更しない。翌日までの範囲へ変更しても、定義による表示の延長として扱う。

シリーズの定義を変更しても、個別例外のidentity・削除状態・overrideFieldsを変更しない。時間を個別変更して別の定義を参照している例外や正確な時刻の例外には、その例外側の指定を優先する。同じ定義を参照する時間の個別変更には、新しい定義を適用する。

### 週・月単位

範囲が変わる場合のみ、定義を参照する全相対予定を保存済み`periodAnchorDate`の週・月内で再解決する。定義選択時の`selectionWeekOffset`/`selectionMonthOffset`を再適用せず、現在日を基準にしない。

- `referenceDate`、`periodAnchorDate`、`parameterSnapshot`は変更しない。
- 再計算したanchorDate・包含endDateのみ更新する。予定のID・タイトル・場所・メモ・色・通知条件・作成時刻・タイムゾーンは維持する。更新した予定のupdatedAtは更新する。
- 「今週中」は今回範囲を編集しない。フェードだけの変更で日付の再解決を行わず、締切曜日snapshotや休日調整済みのendDateも維持する。
- その他の定義もフェードだけの変更では日付を書き換えない。
- 保存済みデータの不正・不整合で安全に再解決できない場合は全体を失敗させ、特定の予定だけ除外して保存しない。個人データをエラーやログへ含めない。

これは相対日付設計4.4の実装であり、既存の「今週中の締切」設定を遡及適用する変更ではない。

### 未定時間

現在の描画に共通設定を使うため、保存済み・繰り返し・個別変更の「未定」にも表示のみ反映する。通知の終了基準は作らない。開始基準の通知時刻は変わらない。

## 7. 原子的保存・競合・通知

domain側のRepository契約に時間表現編集用の読み込み・影響確認・保存commandを追加する。`TemporalDefinitionRepository`を拡張し、featureから複数Repositoryの書き込みを並べて擬似transactionを作らない。commandは変更可能なフィールドだけを受け取り、ID・calendarId・種類・名前・有効状態などは変更不可とする。

影響確認と最終保存の間に他の予定・定義が更新された場合を扱うため、確認結果には定義と影響対象のrevision tokenを含める。実装時は既存のDB revision等を利用し、専用の履歴テーブルは作らない。tokenの選択は実装計画で明示する。最終保存のtransaction内で再照合し、不一致なら再確認へ戻す。

最終保存は次を単一の既存`exclusiveTransaction`内で行う。すべてtransaction callbackの接続を使う。

1. 定義・影響対象を最新状態で取得し、期待revisionと入力を検証する。
2. 相対予定の更新計画を純粋関数で計算し、全件を検証する。
3. 定義と必要な予定日付・updatedAtを更新する。通知条件と例外テーブルは変更しない。
4. 通知に影響する範囲変更では`notification_sync_state.desired_revision`を増やす。
5. commit後に既存の`CalendarRefresh`で表示と通知調整へ変更を通知する。

どこかが失敗したらすべてrollbackする。フェードのみ・未定表示時間のみの変更でも画面を再読み込みするが、通知日時が変わらないため通知revisionを増やす必要はない。未定時間の設定保存は既存settings Repositoryへsetterを追加し、その一行を原子的に保存する。

OS通知操作はDB transactionへ含めない。commitした範囲を既存通知coordinatorが整合させる。今後の通知だけを予約し、過ぎた通知を鳴らさない。無許可でも設定保存は成功させる。再予約失敗時もDBを戻さず、既存の通知エラー表示・再試行・次回起動時の整合処理を使う。「設定保存成功」と「端末通知の整合成功」を区別する。

カレンダーの読み込みは定義・予定・未定設定の同じcommitの状態を使う。相対予定と定義を別commitの状態で組み合わせないよう、既存の読み込み口も必要に応じsnapshot化する。

開いたままの予定編集画面が古い定義・相対予定の範囲を上書きしないよう、保存transactionで参照定義の期待revisionを照合する。不一致なら入力したタイトル・メモ等を保持し、時間表現の最新値を再読込して範囲を再確認できる状態へ戻す。既存相対予定の解決済み日付を古いdraftから無条件に戻さない。

## 8. 責務と永続化

- domain: 定義編集の検証、保存済み期間を基準にした再解決、影響計画・差分。Expo・SQL型は含めない。
- SQLite: 定義・予定のtransaction保存、revision照合、通知revision更新、snapshot読み込み。
- feature hooks: 一覧・編集draft・読み込み世代・保存中の多重操作抑止・競合からの復帰・破棄確認の状態。
- feature components/screens: 表示値とcallbackを受ける。SQLite・祝日ライブラリ・業務計算へ直接依存しない。
- route: Repository配線と既存ナビゲーションだけ。候補は`settings/temporal/index`と`settings/temporal/[id]`。現行の`settings.tsx`と共存できる構成を計画時に確認する。
- 共通UIは実際に他画面でも使うものだけ`src/shared/components`へ置く。既存の選択シート・ドラムロールを再利用する。

`temporal_definitions`と`app_settings`の現在の列・JSON形式で保存可能であり、現段階ではschema追加は不要。既存seed、disable、全Repository実装・テストdoubleへの影響は実装計画で点検する。定義や参照が壊れている場合は初期値で上書きせず読み込みエラーとする。未定時間だけは上記のfallback規則を使う。

現在の定義値と初期値は別に参照できるようにし、標準定義の同じ正本から復元draftを生成する。UIへ初期値をコピーしない。

## 9. アクセシビリティと状態

- 範囲とフェードを色だけで伝えず、文字・操作名・値・選択状態・読み上げを併用する。
- 曜日・日付・時刻・割合の操作領域は44pt以上。小画面と文字拡大ではスクロールでき、ラベルや保存が画面外へ固定されたままにならないようにする。
- 増減には「朝、開始側のぼかしを増やす、現在25%」のような対象付きラベルを付ける。
- 読み込み中の未確定初期値を操作・保存させない。初回失敗は再読み込み、保存失敗はdraftを保持して再試行する。別項目へ移った後の古い非同期結果を適用しない。
- 保存中は二重保存・初期値復元・破棄を抑止する。画面離脱後に古い完了結果で別画面を閉じない。
- 既存のReduce Motion対応を維持する。プレビュー更新に新しい強制アニメーションを追加しない。

## 10. 検証と完了条件

実装ではTDDとし、日本語のテスト名で以下を検証する。

- 日の境界、日跨ぎ、24時間、無効範囲、週の順序、月末・2月・閏年・年跨ぎ、フェードの0/100・合計超過・既存の非刻み値。
- 保存済みperiodAnchorDateからの再解決。来週・来月のオフセット二重適用をしない。「今週中」の締切・休日調整snapshotと期間を維持する。
- 日単位のシリーズ、削除例外、同じ/別の定義や正確な時刻へ変更した例外の表示・通知。開催identityを維持する。
- 定義＋相対予定＋通知revisionのcommit/rollback、途中の不正・DB失敗、影響確認後の競合、古い予定draftの保存競合。
- 保存前はDB不変、キャンセルと初期値復元、失敗後のdraft保持、再試行・二重操作・unmount後の完了、他設定へ影響しないこと。
- 定義と予定の一貫したsnapshot、ビュー間の再表示、フェードのみ/未定表示のみで通知時刻が変わらないこと、範囲変更後に未来通知が再計算されること。
- 未定設定の既定・永続化・不正値fallback。予定の実終了や通知条件は作らない。

通常のtypecheck・lint・全Jest・diff checkに加え、UI配線を含むiOS/Android exportを実行する。追加のExpo API・依存を扱う場合は実装前にSDK 57固定の公式資料を確認する。現時点で新規依存は予定しない。

実機確認は別記録とし、小画面・文字拡大・VoiceOver/TalkBack、ライト/ダーク、戻る・破棄・ドラムロール、アプリ再起動、日跨ぎと各ビューの描画、端末通知の再予約を確認する。自動テスト成功をもって実機確認済みとはしない。

README・DB保存仕様・関連設計書へ設定の追加と反映規則を記載し、Issue #60の受け入れ条件と照合する。
