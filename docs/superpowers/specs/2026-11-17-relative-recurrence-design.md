# 週・月の時間表現の意味を保つ繰り返し

## 状態・関連

- Issue #61。承認済み設計に基づく実装・自動検証済み。native build・実機は未確認。検証結果は`docs/verification/2026-11-17-relative-recurrence.md`。
- 既存の単発相対日付、繰り返し例外、端末通知、時間表現設定（#60）の設計を拡張する。
- 確認済み: 週・月の両方を対象にする。「今週中」は初回が水〜金でも次回以降は月〜金。調整先の平日がない週も元の締切で残し、要確認と示す。週↔月の変更では表示されている開始日を基準にし、終了対象期間は新しい単位で選び直す。
- 終了条件・入力構成・モデル・保存方法は本書全体の承認により確定した。
- 設計承認後は実装計画を作成し、計画の再承認を求めず実装・検証・PR作成まで進める。

## 1. 目的

「月初を毎月」「下旬を毎月」「今週前半を毎週」のような予定を、各対象週・月の定義から毎回解決する。元予定の開始日・長さを単純に足す方式は使わない。たとえば月末5日間なら2月も3月も、その月の末日から5日間を計算する。

既存の正確な予定・日内ざっくり予定・終日予定の繰り返し、単発相対予定、保存済み通知・個別例外を変更せず、新しい繰り返しの意味をversionで区別する。

## 2. 初回の対応範囲

- 週の8定義: 今週中、今週前半、今週後半、今週末、来週、来週前半、来週後半、再来週。
- 月の6定義: 月初、上旬、中旬、下旬、月末、来月。
- 週定義は毎週・N週ごと、月定義は毎月・Nか月ごと。Nは既存同様の正の安全な整数とし、12か月ごとも利用できる。
- 終了なし、指定した対象週・月まで、回数指定。
- 作成・編集・1日/2日/週/月表示、個別変更・削除、これ以降・シリーズ全体の変更、未来の端末通知。
- #60の範囲・フェード編集に追随する。

日/年という別単位の指定、曜日の複数選択、任意の時間表現追加、自然言語解析、独自業務日カレンダー、外部同期は対象外。年ごとの相対予定は必要なら12か月ごとで表現する。通知予約エンジンの予算・権限・補充方針は変更しない。

## 3. 利用者向けの動き

### 3.1 作成・編集

週・月の時間表現を選んだ場合も「繰り返し」を有効にする。週なら「繰り返しなし／毎週／カスタム」、月なら「繰り返しなし／毎月／カスタム」を既存の単一選択部品で表示する。カスタムは対応する週または月に単位を固定し、間隔と終了条件を編集する。

- ラベル例: 「毎月・月末5日間」「2週ごと・今週前半」。単に「毎月1日」などと表示しない。
- 「来週」「再来週」「来月」のoffsetは初回対象を決めるためだけに使う。各回で再加算しない。
- 予定の基準日pickerは単発相対予定と同様にdisabled。現在の解決済み初回期間と、次の2回の期間を文字で確認できるようにする。
- 間隔・回数の不正値、単位と定義の不一致、終了対象が初回より前の場合は保存不可。計算が表現可能な日付範囲を越える場合は安全に展開を打ち切り、Invalid Dateや無限loopを生じさせない。
- ざっくり/きっちりのタブや別の定義へ切り替える際はdraftを保持する。週から月など単位の互換性がなくなった場合、見えない無効な規則を保存せず「繰り返しなし」へ切り替えた理由を示す。保存まではDBを書き換えない。
- 既存の単発相対予定に繰り返しを付ける場合、初回の保存済み期間・締切条件を維持する。設定変更を黙って適用しない。

新規の「今週中」の締切曜日・休日調整は保存時の設定をシリーズへ保持する。既存予定からの変換では保存済みsnapshotを引き継ぐ。現在の設定を使い直す場合は明示的な「締切条件を現在の設定に更新」操作を行い、変更範囲と初回・次回の期間を確認する。

### 3.2 終了条件

- 「終了なし」: 検索・通知の要求期間内だけを有限に展開する。
- 「指定週まで／指定月まで」: 日付pickerの選択をその週の月曜または月初へ正規化し、「2026年11月16日の週まで」「2027年2月まで」のように最終対象期間を表示する。その期間の末尾がpickerで選んだ日より後でも期間全体を含める。
- 「回数」: 初回を1回とし、各対象週・月で1回数える。初回が途中からでも1回。個別削除・要確認fallbackも回数を消費し、後の開催を追加して穴埋めしない。
- 間隔は初回対象期間から固定する。2か月ごとの予定に個別例外があっても、元の対象月の並びは変わらない。

上記の終了条件は新しい意味ベースの繰り返しだけのUIとする。既存V1の「日付まで」の意味は変えない。

## 4. 各回の範囲解決

### 4.1 共通

最初の`periodAnchorDate`を基準に、暦週または暦月をN単位ずつ進める。週はカレンダー表示の週開始設定と独立に月曜基準を維持する。

初回は保存した期間と解決条件を使う。次回以降はその対象期間を基準として最新の時間表現定義を適用し、表示用の解決済み予定を作る。各回を実体レコードとして大量保存しない。

- 週定義の開始・終了曜日を対象週へ当てはめる。
- 月の日付は既存同様、存在しなければ対象月末へ丸める。「29日〜月末」は平年2月なら28日だけ、閏年なら29日だけ。
- 「月末5日間」は2月28日なら24〜28日、3月31日なら27〜31日。月ごとの長さを引き継がない。
- 年跨ぎ、月跨ぎ、DSTは通常ケースとして扱い、固定ミリ秒による日移動をしない。
- 発生回は対象期間と実際の表示期間を別の値として扱う。検索窓と実範囲が重なる開催だけを返す。

### 4.2 今週中

例として、水曜日に金曜締切で登録した初回は水〜金。次の対象週からはその週の月〜金となる。初回の「水曜日」を次週へ持ち越さない。

- 締切曜日はシリーズ保存時の値を使う。設定を金曜から日曜へ変えても、保存済みシリーズの未来回を含めて自動変更しない。
- 土日祝を前倒しするか、日本の祝日を使うかもシリーズ保存時に固定する。各対象週の祝日の日付はその週のProvider結果から計算し、初回の調整済み日付をコピーしない。
- 初回の保存済み調整結果は維持する。新しく繰り返しを作る初回で調整できない場合も、次項のfallbackを使う。繰り返しなしの既存の保存エラー規則は変更しない。
- 初回の基準日がその週の締切より後の場合は、単発の既存規則どおりその基準日1日とする。次の対象週から通常の月曜〜締切を使う。

### 4.3 調整不能・祝日情報未対応

次の場合はその開催を消さず、休日調整前の期間を使って「締切を要確認」と表示する。

- 対象範囲に調整先の平日がない。
- 保存した日本祝日設定の対象期間がProviderの対応範囲外。

範囲を別の週へ移したり、前の週の平日へ勝手に遡ったりしない。理由は「調整先の平日がありません」「祝日情報に対応していません」と文字と読み上げで示す。色だけで伝えない。通知もfallbackの締切を基準にし、通知文面へ要確認であることを付ける。通知自体を黙って削除しない。

初回fallbackでは、試みた休日調整条件を既存の`deadlineAdjustment`へ保存し、実際には調整できなかったことを`deadlineWarning`で区別する。`unadjustedDeadlineDate`はfallback前の締切、`calendarId`は試みた祝日設定とする。警告だけを保存して調整条件を失わないようにする。理由は再起動後も維持し、未来回の理由はその回の解決結果に含める。通常の業務データ不整合や未知のrule versionは休日fallbackに混ぜず、従来どおり読み込み・展開エラーとして扱う。

## 5. 定義変更と保存済み条件

#60で承認した「時間表現の範囲を変えると保存済み予定へも反映」を、新しいシリーズにも適用する。初回の保存範囲は保存済み`periodAnchorDate`内で原子的に再解決し、以降の各回は同じ定義の最新値から再計算する。過去の開催も対象となる。

- 対象週・月の並びと開催identityは変えない。月初の終了を5日から7日へ変えても、別の対象月へは移動しない。
- フェードだけの変更では日付・締切snapshotを書き換えない。
- 今週中の締切曜日・休日調整条件は定義編集と別の保存済み条件であり、最新のアプリ設定へ置換しない。
- 定義更新、必要な初回・置換予定の再解決、更新時刻と通知revisionは同じtransactionに含める。無限の未来回を書き出す処理は行わない。
- 個別に日時・定義を変更した例外はその指定を優先する。同じ定義を参照する相対予定の例外は、#60と同様その定義の編集を反映する。
- 定義が無効化されても、保存済みシリーズが参照する定義は取得し、描画・展開を続ける。

## 6. モデルと永続化

### 6.1 繰り返し規則

`RecurrenceRuleV1`はそのまま残し、unionへ次の別形式を加える。

```ts
type RelativeRecurrenceRuleV2 = Readonly<{
  version: 2;
  kind: 'relativePeriod';
  frequency: 'weekly' | 'monthly';
  interval: number;
  end:
    | { type: 'never' }
    | { type: 'untilPeriod'; periodAnchorDate: string }
    | { type: 'count'; count: number };
  deadlinePolicy: null | {
    version: 1;
    weekday: 5 | 6 | 7;
    adjustNonWorkingDays: boolean;
    holidayCalendarId: 'jp' | 'none';
  };
}>;
```

初回の基準・対象期間は既存の`FuzzyResolutionContextV1.referenceDate/periodAnchorDate`を正とし、ruleへ重複して保存しない。時間表現IDは予定側を正とする。`deadlinePolicy`は今週中だけ必須、その他はnull。初回snapshotの締切曜日・休日調整の有無/カレンダーと矛盾しないことを検証する。既存予定で休日調整snapshotがなければ調整OFFとして引き継ぎ、現在のアプリ設定から推測しない。新しいfallbackではsnapshotと警告を両方保存するため、調整ONと矛盾しない。繰り返しを外して単発へ変更しても、残す回の期間・snapshot・警告を維持し、再び繰り返しを付けたときはその条件を引き継ぐ。

初回のfallbackを記録するため、既存contextの`parameterSnapshot`にoptionalな`deadlineWarning`（`noBusinessDay | unsupportedHolidayRange`）を加える。通常の旧contextは変更不要。開催の表示モデルにはoptionalな同じ警告と対象期間を含める。

V2は週・月の相対fuzzy予定かつ対応frequencyだけに許可する。正確・終日・日内fuzzyにはV2を保存せず、週・月相対予定にV1を付けることも禁止する。未知versionをV1へ読み替えない。

### 6.2 保存形式と互換性

既存の`events.recurrence_rule_json`にV2を保存し、context JSONへoptional情報を追加する。例外は専用テーブルのまま使う。新しいテーブルや全開催の保存、破壊的な一括変換は不要で、現時点ではschema version 7の列構成を維持できる。

parser、row mapper、Repositoryの整合性検証、editor draftの相互変換、通知・表示のreaderを同じ変更で対応させる。既存V1とrecurrence=nullのレコードは自動でV2へ変換しない。古いアプリへV2を渡す下位互換は保証せず、アプリの更新前データを新しい実装が非破壊に扱うことを保証する。

## 7. 開催identity・個別例外・シリーズ分割

### 7.1 安定したidentity

既存の`{seriesEventId, originalOccurrenceDate}`という組は維持する。V1は従来の元開始日、V2では対象週の月曜日または対象月の1日を`originalOccurrenceDate`とする。表示開始日とは明確に分離する。

たとえば下旬の「2027年2月21日開始」の開催は、V2では2027-02-01を識別日として扱う。定義編集や休日調整で表示開始・終了が変わっても、同じ月の例外・編集リンク・通知タップ先は変わらない。

開催の有効性を調べる処理は「識別日1日と実範囲が重なるか」で判断せず、対象期間がシリーズの間隔・終了条件に属するかを計算する。表示範囲外へ移動した例外も、現在の検索先で表示できるようにする。

### 7.2 個別変更

- この予定だけの編集は、同じ対象期間identityへ通常の単発置換予定を保存する。置換自身は繰り返さない。
- タイトル・メモ・色・場所・通知だけを変えた例外では、元の開催を各対象期間へ解決した最新の時間範囲を継承する。identityの日付へ予定を移すV1の処理をそのまま流用しない。
- 時間のoverrideがある例外だけは、その置換の日時・定義・contextを優先する。通知だけのoverrideはその回だけの通知を使う。
- 削除・再編集は同じ1行の例外を更新し、例外の入れ子は作らない。
- 日時だけの変更は繰り返し規則の編集と区別する。週↔月・きっちりへの変更や、異なる単位に変更済みの例外の再編集も単回で保存できる。対応する繰り返しを選び直すまでは、この場合の範囲を「この予定」に限定し、理由を表示する。
- 「締切を要確認」は実際に使う時間の解決結果に従う。時間を正確な予定へ個別変更した回には元シリーズの警告を持ち越さない。

### 7.3 これ以降・シリーズ全体

既存と同じ3範囲の選択を維持する。これ以降は対象期間を境界として通常シリーズに分割する。

初回の解決範囲だけを全体変更する場合、その範囲を保存し、未来回の規則に変更がなければ後の例外は維持する。後の回から本文だけを全体変更した場合は、元の初回期間を維持する。

- 内容だけの変更: 対象期間の並び・締切policyを維持し、以降の例外を同じ対象期間へ引き継ぐ。新シリーズの最初の期間は、その開催で実際に使っていた基準と範囲を採用する。元の初回の水曜日を再適用しない。
- 規則・間隔・週/月の種類・時間表現・締切policyを変更する場合: 対象範囲の例外リセットを明示して確認する。ユーザーがキャンセルしたら全データを維持する。
- 繰り返しを外す変更は既存同様にこれ以降／シリーズ全体の確認を行う。これ以降では前のシリーズを境界前で終了し、境界回を単発として残す。シリーズ全体では現在のシリーズの初回を単発として残す。単発化しても残す回の解決済み期間・snapshot・警告は保持する。
- 回数を変えない分割では、分割前の対象期間数を差し引いて残回数を引き継ぐ。削除例外も既定の対象期間数に含める。
- シリーズ全体の内容だけの変更は、現在のシリーズの初回期間を移動させず、対象期間identityと例外を保持する。表示開始日と識別日の差を日数offsetとして全期間へ適用しない。
- 同じ週/月単位のまま規則を変更する場合は、新しい条件から再構築し、変更対象の先頭の対象週/月を初回としてpreviewする。「来週」のoffsetを繰り返し適用しない。
- 週↔月へ変更する場合は、識別日ではなく変更対象の先頭回の表示開始日を、新しい単位の期間へ対応付ける。「これ以降」は開いている境界回、「シリーズ全体」は現在のシリーズの初回を先頭とし、確認画面にその開始日を明記する。11月30日の週に属していても12月3日開始なら、月単位への変更後は12月を初回対象とする。新規選択時の「来月」等のoffsetを追加適用しない。
- 単位を変えた場合、旧「指定週まで／指定月まで」の終了対象は自動変換せず、新しい単位での再指定を必須とする。終了なし／回数は互換な値を維持し、分割時の残回数規則を適用する。保存前に初回・次の2回・終了条件を再確認できるようにする。
- 削除はこの回だけ／この期間以降／現在のシリーズ全体を対象とする。分割前の過去シリーズには遡らない。

上記の規則変更の分類・例外リセットはV2へ追加し、V1で既に承認済みの挙動は変更しない。新シリーズID・例外付け替え・置換削除・通知revisionは既存の単一transaction保存境界で処理し、競合したら全部失敗させる。

## 8. カレンダーと端末通知の共通解決

domainに、対象期間の列挙・個々の期間解決・identity検証の純粋関数を置き、カレンダー、通知、例外編集・分割で同じ規則を使う。祝日情報は既存`HolidayProvider`境界から供給し、domain/UIへ外部ライブラリ型を漏らさない。

- 依存の組み立て側が保存済み`deadlinePolicy`に対応する日本/なしProviderを選ぶ。現在のアプリの表示用祝日設定で保存済みシリーズの条件を置換しない。
- カレンダーと通知の展開へ定義と祝日解決環境を渡す。現在の`expandEventOccurrences`、`loadValidOccurrence`、`materializeOccurrenceReplacement`、シリーズ変更計画のV1専用仮定を点検し、versionごとに分ける。
- RepositoryはSQLで祝日を計算せず、必要なシリーズ・定義・例外・置換予定を一貫したsnapshotで取得する。SQLの日付条件はV2の初回の表示開始日だけに依存せず、対象期間と移動例外を取りこぼさない形にする。
- 時間表現編集の確認token、予定保存の期待定義token・シリーズrevisionを維持する。古いdraftが定義更新前の日付を戻さないよう、再確認時にもV2を再解決する。
- 開催読込は元予定・置換予定の定義tokenを解決結果と同じtransactionで返す。編集画面はこのtokenを優先し、後から読んだ定義一覧のtokenと古い開催の組み合わせで保存しない。
- 通知は各回の実際の開始/包含終了から計算する。初期値の「終了日の前日9:00」はその回の終了日に基づき、個別の通知設定と通知なしを維持する。
- 通知ID・タップ先は対象期間identityで安定させ、時刻・範囲・警告が変わればfingerprintも変えて再予約する。警告はタイトル等の個人データとは別の安全なラベルから構成する。
- 通知予算60件、366暦日、起動・復帰等での補充、権限、過去の通知をまとめて鳴らさない方針は変更しない。

日付・範囲の解決が同じでも、DB保存成功とOS通知の整合成功は別に扱う。通知の再予約失敗で予定や定義をrollbackせず、既存の再試行を使う。

## 9. エラー・アクセシビリティ・実装境界

- 文面は「毎月・下旬」「締切を要確認」など、意味を文字で説明する。グラデーション・色だけに依存しない。
- 既存の共有選択シート・日付picker・編集画面を利用し、新しいrouteやnative依存は原則追加しない。共通UIは本当に共用する場合だけ`src/shared/components`へ置く。
- domainに週/月解決とversionルール、SQLiteにJSON/row/transaction、feature hookにdraft・非同期調整、表示modelにラベル・警告を置く。
- 初期化失敗を空の繰り返しや既定の締切で埋めて保存しない。再読込でき、失敗してもタイトル・メモ等を維持する。
- 44pt、文字拡大・小画面、VoiceOver/TalkBack、ライト/ダーク、Reduce Motionを既存と同じ基準で扱う。
- 予定保存まではインメモリ。取消・例外リセット確認のキャンセルでDBを変更しない。個人データをログや外部へ送らない。

## 10. 実装計画で具体化する箇所と検証

新しいAPI名・ファイル分割、ResolverへProviderを渡す形、SQLの絞り込み・indexの必要性、既存UIのdraft型の分割は実装担当が決める。新たなDB制約やnative依存が必要と判明した場合は、目的と影響を説明して設計との差分を確認する。

- 14種類の初回・2回目・間隔指定、来週/来月offsetの一度だけの適用、初回部分週・締切後の初回。
- 2月・閏年・月末日指定・月末日数・年跨ぎ・DST・対象期間全体と重なる検索、日付の表現上限・大きな間隔の安全な終了。
- 回数・最終対象期間・個別削除による非補充、元期間と表示開始の異なる例外の有効性・移動・再編集。
- 保存済み締切/休日policyを設定変更で書き換えないこと、週全体が休日・祝日情報未対応のfallbackと読み上げ・通知ラベル。
